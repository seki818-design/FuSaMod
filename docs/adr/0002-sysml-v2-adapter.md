# ADR-0002: SysML v2 アダプタ方式

- 状態: **A(公式パイロット実装)を採用方向。PoC で実現性を確認済み。** 運用方式(常駐サービス化など)は P1 で詰める。
- 候補: A) Eclipse SysML v2 パイロット実装(Java)をサービスとして利用 / B) Langium による TS パーサー / C) 完全自作

## PoC の結果(2026-10)

公式パイロット実装(conda-forge の `jupyter-sysml-kernel` 0.62.0 に同梱の fat jar)を、Jupyter を介さず Java から直接呼んだ。

| 項目 | 結果 |
|---|---|
| 呼び出し | `SysMLInteractive.process(text)` で解析・検証・要素グラフ取得ができる(headless) |
| 検証の質 | 未解決の参照・型の誤り・不正な enum 値・未知の属性・ステレオタイプの適用先の誤り(`annotatedElement` 制約)・二重指定を検出 |
| 抽出 | `tools/sysml-check/SysmlExtract.java` が、SCDL に依存しない要素グラフ(JSON)を出力。`scdlFromGraph` が SCDL モデルに変換し、元モデルと完全一致(2 例) |
| コスト | 1 回の実行で約 10 秒(大半は標準ライブラリの読み込み)、ピークメモリ約 640MB、jar 約 133MB、Java 21+ が必要 |
| 再現性 | `tools/sysml-check/run.sh` / `extract.sh`。jar はバージョンと SHA256 を固定して取得。生成グラフはコミット済みと一致(決定的) |

### 評価

- **A は実現可能で、検証の質が高い。** SysML v2 準拠を必須とする要件に合う。
- **常駐サービス化が前提。** 起動に約 10 秒かかるため、リクエストごとの起動は不可。ライブラリを読み込んだ JVM を保持し、
  モデルの編集ごとに再解析する。大規模モデルでの性能・増分解析は未評価。
- **API の安定性がリスク。** 今回使った `SysMLInteractive` は Jupyter カーネルの内部 API で、安定した公開ライブラリ API ではない。
  対策: バージョンと SHA256 の固定、出力を汎用の要素グラフ(JSON)に限定してアダプタ層で隔離する(本ツールの他の部分は Java に依存しない)。
- **B は今回未評価。** 参考として第三者製の ANTLR 実装(`sysml-v2-lsp`)を試したところ、構文は見るが未解決の参照などの意味エラーは検出しなかった。
  よって準拠性の検証には使えない。B を採るならエディタ補助(構文ハイライト等)に限定する。
- **ライセンス**: リリースリポジトリの表記では EPL-2.0。ただし fat jar に同梱された第三者ライブラリのライセンス確認は未実施(配布前に法務確認が必要)。

## 決定(暫定)

1. 準拠性の検証・要素グラフの取得は A(公式パイロット実装)で行う。
2. 安全分析コア(`@fusamod/safety-core`・`@fusamod/scdl`)は SysML 要素を `modelRef` や要素グラフ経由で参照するだけにし、アダプタ層で隔離する。
3. P1 で、常駐サービス化・増分解析・大規模モデルの性能・SysML API(REST)との関係を評価して確定する。

## 残る PoC 項目

- 編集 → 再解析の往復(テキストを書き換えて再検証)の遅延
- 大規模モデルの性能とメモリ
- 構造(part の分解)・要求・フロー・action を要素グラフに加える(現状は SCDL 用の最小セット)
- jar の第三者ライセンスの棚卸し
