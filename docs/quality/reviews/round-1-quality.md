### B2. 性能効率性 — 採点 86 / 外部確認待ち減点 4

証拠
- `pnpm bench`(再実行): N=5000 で一括解析 374 ms、構造図レイアウト 707 ms、SCDL レイアウト 479 ms、FMEA CSV 41 ms、すべて予算内。典型的な規模(数十〜数百要素)では体感の遅延なし。`analysis.json` は N=5000 で 13.3 MB。
- API 応答: `GET /api/projects/ev-powertrain` 約 55〜65 ms(15 KB)、履歴 33 ms、静的 index 3.6 ms。Java は初回 6.8〜8.1 秒、以後 20〜80 ms(常駐)。
- `FUSAMOD_IT=1` の結合テストで Java の解析時間を確認した。

減点理由
1. **版が増えるほど保存が遅くなる**: 130 回の保存で 30 ms から約 180 ms に増加した。`ProjectStore.latestMeta()` が呼ばれるたびに `.history` の全 `meta.json`(最大 100 件)を読み直し、1 回の保存で複数回呼ばれる(`read`、`saveModel`、`snapshot`)。版ごとにモデルと `safety.json` と `model.graph.json` を丸ごと複製するため、容量も増える(100 版で 2.8 MB、小さなデモでの値)。
2. 静的資産に圧縮(gzip/br)がなく、ハッシュ付き JS(330 KB、ソースマップ 979 KB)に `Cache-Control: max-age=0`(`immutable` 未設定)。
3. スナップショット解析の `findGraphByModelHash` は、解析のたびに全プロジェクトのモデルを読んでハッシュ照合する(プロジェクト数に対して O(n))。
4. `PUT /model` は、`MAX_MODEL_BYTES`(2 MB)の検査より前に解析(Java 呼び出し)を実行する。マルチバイト文字で 2 MB を超える本文(zod は 200 万文字まで許可)は、解析した後に 413 となる。
5. 負荷試験(同時接続、メモリ使用量の計測)は未実施。ベンチは合成データのみで、実プロジェクトでの計測は無い。

### B5. 信頼性 — 採点 84 / 外部確認待ち減点 3

証拠は 2 章の「信頼性」の表を参照(Java の強制終了からの自動復旧、構文エラーの診断、スタックオーバーフロー後の継続、楽観的排他の同時実行、再起動後の永続性、壊れたファイルの検出)。アトミックな書き込み(一時ファイル → rename)、プロジェクト単位のロック、`SIGTERM` での終了処理もある。

減点理由
1. **複数ファイルの更新が一括ではない**: `saveModel` は `model.sysml` → `model.graph.json` → スナップショット → 監査の順に書く。途中でプロセスが落ちると、現在の状態と履歴(リビジョン)や監査ログが食い違う。復旧手段は無い。
2. 履歴は **100 版で黙って削除される**。`docs/operations.md` は「全リビジョン」「`history/`」と書くが、実際は `.history/` で 100 版まで(ドキュメントと実装の矛盾。安全分析の記録としては、削除が警告なしである点が弱い)。
3. ロックはプロセス内のみ(複数プロセスで同じディレクトリを共有すると保護されない)。ドキュメントに制約として書かれていない。
4. 壊れた `safety.json` / `proposals.json` は 500 を返すだけで、自己修復・退避・自動での最終正常版への案内が無い(履歴からの復元は成功するが、利用者が気づく導線が無い)。
5. 監査ログへの追記はロックされない(並行時に行が交錯する可能性。小さな行では実害は出にくい)。
6. AI 提案の適用は「安全データの保存 → 提案の状態更新」が 2 段階で、間で落ちると、適用済みなのに pending のままになる(再適用は検証で防がれる可能性が高いが、未確認)。
7. 長時間運用・障害注入(ディスク満杯、権限エラー)は未検証。
