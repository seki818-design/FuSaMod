## 2. 第 9 回の指摘の実測(バンドル版・実 HTTP)

試験用の重いモデル: 12,000 段の特化(`part def P1 :> P0; …`、約 300 KB)を `heavy` プロジェクトとして保存。

### 2.1 同時要求の重複排除 — **修正を確認**

| 試験 | 結果 |
|---|---|
| サーバーを新規起動(記憶なし)して、`GET /api/projects/heavy/export/fmea.csv` を**同時 5 件** | 5 件とも **504、68.88〜68.89 秒**で一斉に完了(R9: 74/146/219/288/355 秒の直列)。JVM を占有したのは 1 回分だけ |
| 続けて逐次 2 回 | 504 が **0.0145 / 0.0151 秒**(記憶が効く) |
| 別の新規サーバーで viewer が `GET /api/projects/heavy` | 200、68.9 秒、本文に `"sysmlFailure":"timeout"`。2 回目は 0.016 秒 |

対応は `services.ts` の `inflight`(ハッシュ単位の Promise の共有)。回帰テスト(`fake-processes.test.ts`)は 5 件の同時要求で `calls == 1` を確認しており、R9 で見逃した「同時」を押さえている。

### 2.2 viewer の `/analyze` の制限 — **文書どおりに動くが、占有は防げていない**

| 試験 | 結果 |
|---|---|
| viewer が 12,000 段(約 300KB)のモデルを送信 | **413**(0.018 秒)。文言は日本語で正しい |
| viewer が 7,000 段(**187KB**、200KB 未満)を送信し、1 秒後に別の 187KB を送信 | 2 件目は **429**(0.013 秒)。同時 1 件の制限は効く |
| 上の 1 件目(187KB)は | 200(`sysmlFailure:"timeout"`)、**76.7 秒** |
| viewer の 1 件目の 2 秒後に、編集者が自明なモデル(2 要素)を `/analyze` | **200、84.7 秒**(約 82 秒待たされた) |
| 編集者が単独で同じ 187KB を送信 | 200、66.1 秒(タイムアウト) |

結論: 「editor が viewer に待たされないか」は **No**。200KB のサイズ上限は、重さの上限にならない(187KB のチェーンでもタイムアウトまで JVM を使う)。上限は「内容の大きさ」ではなく「解析時間」で見るべき。再現: 上の表のとおり(`POST /api/projects/ev-powertrain/analyze` に `package H { part def P0; part def P1 :> P0; … P7000 :> P6999; // a }` を viewer のトークンで送り、直後に編集者が小さなモデルを送る)。
`security.md` は「完全な防止ではない（モデルを少しずつ変えながら、上限の範囲で占有することはできる）」と明記しており、文書と実測は一致する。実装側の追加策(編集者優先の待ち行列、viewer の解析時間の予算、切断時の取り消し)は無い。

## 3. 新たな欠陥(今回)

1. **(中)viewer の 187KB のモデルが編集者を約 82 秒止める**(2.2)。サイズ上限が重さを制限しない。優先度つきの待ち行列(編集者優先)か、viewer の解析時間の予算(例: 15 秒でそのモデルだけ打ち切る)が必要。
2. **(低)停止中の文言が紛らわしい**: SIGTERM で拒否された要求に `Java が使えない` / `保存済みグラフに切り替えます` と出る(2.3)。
3. **(低)E2E が `TMPDIR` のパスが長いと起動できない**: Chromium のプロファイルの置き場が `TMPDIR` 依存で、README にも注意がない(今回の検証では環境側の事情と判断したが、CI やコンテナで `TMPDIR` を深い場所にすると再現しうる)。
4. **(低)viewer が `safety` を最大 5MB(`bodyLimit`)まで送れる**: 200KB 制限は `model` のみ。`safety` の大きさでの CPU 負荷は今回測っていない(未検証)。
