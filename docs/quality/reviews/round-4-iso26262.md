## 敵対的探索の結果

### 修正の網羅性(ASIL 継承)— 抜け道は見つからなかった
次を試し、いずれも期待どおりの指摘が出た: 分解先の子孫の引き下げ(1 段・2 段)、親と異なる元 ASIL を名乗る子孫、`originAsil` だけの孤児要求、D→D+QM(D) の分解先の子孫、再分解(警告 `REDECOMPOSITION`)、分解先が祖先要素・同一要素・未配置、分解元の二重分解、分解先の再利用、自己分解・循環、要求の ID 重複、親を外して別の安全目標へ付け替え(`REQ_BELOW_GOAL_ASIL` / `GOAL_NO_FSR`)、安全目標 ASIL を下げて事象とずらす(`GOAL_ASIL_MISMATCH`)。ISO 26262-9 の分解表(D: D+QM / C+A / B+B ほか)と HARA 表(S+E+C の合計規則)は正しい。

挙動上の注意点(欠陥ではなく仕様の癖): 分解先 B(D) の子孫が `originAsil` を省略して `asil: B` とだけ書くと、`REQ_BELOW_GOAL_ASIL`(誤検出に近い)が出る。「子孫は元 ASIL の表記を引き継ぐ」という規則の帰結で、安全側ではあるが、利用者に表記の強制を理由なく見せる。AI 提案がこの形で毎回却下される可能性がある。

### R4-1 意図機能・安全機構の ASIL が検証されず、黙って下げられる(高。ラウンド 3 と同種)
`validateAsilInheritance` が見るのは `safetyRequirements` だけである。`intendedFunctions[].asil/originAsil` と `mechanisms[].asil/originAsil` は、要求・安全目標・分解のどれとも突き合わされない。実行結果(サンプル ev-powertrain):

| 変更 | 指摘 |
|---|---|
| IF-1(B(D))を `asil: QM`、`originAsil` 削除、`requirementIds: []`、ペア削除 | **警告 1 件のみ**(`MECHANISM_UNPAIRED`)。`NO_SAFETY_MECHANISM` も消える(QM は対象外のため)。ASIL D の安全目標に紐づく意図機能が、QM として「整合」に見える。 |
| IF-1 を `asil: QM, originAsil: D`(分解でも何でもない) | 警告 `GROUP_MIXED_WEIGHT` のみ(要求グループに混ざる場合に限る)。`DECOMP_ORPHAN` 相当のエラーは出ない。 |
| SM-1 を `asil: QM, originAsil: D` | 警告 `GROUP_MIXED_WEIGHT` のみ。 |
| IF-1 を `asil: D`、ペア削除 | 警告 `NO_SAFETY_MECHANISM`(エラーではない)。 |
| 追加: AI の `addIntendedFunction`(`asil: QM`)、`addMechanism` | 200 で適用(新エラーなし)。 |

SCDL ビュー・パズルビュー・ペアリング(`PAIR_DECOMP_INVALID`)は意図機能と安全機構の ASIL を重みとして使うため、ここでの誤りは、設計の「ペアとデコンポジション」(本ツールの中核機能)の表示を直接誤らせる。safety-notes の検出表は「要求の ASIL」と書いており**過大記載ではない**が、検出しない誤りの一覧(「検出しない」節)にも書かれていないため、利用者は検査されていると思いうる。ルーブリックの「不正確な安全上の振る舞い」には直接当たらない(誤った計算ではなく未検査)が、ラウンド 3 と同じ「ASIL の黙った引き下げ」の経路なので、B1 で -8、C1 で -5、A1 で -4 とした。

### R4-2 AI 提案のゲートは「リスクを下げる変更」を止めない(中)
`apply` の関門は「新しいエラーが増えない」ことだけを見る。実 API で次を確認した。
- `setSeverity`(FE-1: 10 → 1)→ **200 で適用**。続けて `setLinkRatings`(発生度 1・検出度 1)→ 200。最大 RPN が 150 から 80 に下がった。指摘も警告も増えない。
- `aiChanges` には提案 ID と件数 `operations: 1` しか残らず、どの故障の重大度を何から何へ変えたかは安全データ内に残らない(監査ログにも提案 ID と件数のみ)。
- 重大度(FMEA)とハザード分析の S は、どこでも突き合わされない(`FM severity lowered everywhere` → 指摘ゼロ)。HARA の S3 に紐づく故障影響の重大度を 1 にしても検出されない。これは AI に限らない。

承認者が内容を確認する責任は文書で述べられているが、「AI は追加・設定のみ」という安心感の一方で、設定(上書き)が最も危険側の操作になりうる。前回の提案どおり、変更前後の値を来歴に残す、または「評価値を下げる提案」を別枠で明示するべき。

### R4-3 FTA
- `topProbabilityUpperBound` は未展開・範囲外で `undefined`(OK)。
- `singlePointFaults` は未展開の事象を含む AND でも `complete: true`(未展開の事象が単独で十分かもしれない)。`FT_UNDEVELOPED` 警告と画面表示はあるので、致命ではない。API を単体で使う利用者には誤読の余地がある。

### R4-4 `MECH_DC_D_MISMATCH` と文書の食い違い(中〜低)
- 実装: `diagnosticCoverage` が `high` なら対象故障のリンクの検出度 D ≤ 3、`medium` なら D ≤ 5 を超えると**警告**。`low` と DC 未設定は検査しない。D が未評価なら何も出ない。リンクごとに同じ警告が複数出る(重複)。
- 検出は動作する(SM-1 を `high` にすると 3 件)。ただし閾値(3・5)は ISO 26262-5 や AIAG-VDA に根拠の無い経験則で、コードにも文書にも出典が無い。DC(ISO 26262-5 の 60/90/99%)と FMEA の D(1〜10)の対応は規格が定めていない。
- サンプルの SM-1 は、この検査を通すために `high` から `medium` に**変更された**(git diff で確認)。主張を弱める方向なので誠実ではあるが、「検査に合わせてデータを直した」という事実は応答書にしか無く、サンプルの根拠が示されていない。
- `docs/safety-notes.md` は「`diagnosticCoverage` は記録のみ」と書いたままで、`MECH_DC_D_MISMATCH` を「検出する」表にも載せていない。「検出する」の主張は過大ではないが、**文書が実装より少なく書いている**(トレーサビリティの欠落)。

## ISO 26262-8(ツール認定)の観点と、実装の欠陥との区別

**実装の欠陥(コードで直せるもの)**: R4-1(意図機能・安全機構の ASIL 未検査)、R4-2(AI の評価値上書きの来歴と関門)、R3-5(`aiChanges` の改ざん・要素 ID 無し)、R3-4(根拠の形式検査と、警告のまま保存できる点)、`MECH_DC_D_MISMATCH` の閾値の出典と文書、`REQ_BELOW_GOAL_ASIL` の誤検出に近い挙動、時間依存で不安定なテスト、サーバーの回帰テスト欠落。

**ツール認定(ISO 26262-8 第 11 章)の観点で、アセッサが今も受け入れない点**(実装では直せず、組織の手続きと証拠が要る):
1. TI/TD/TCL の正式な判定と、ツールの使用ケース(どの成果物の作成・検証に使うか)の一覧が無い。safety-notes は「TD2 以上を想定」「認定の証拠を提供しない」と正直に書くが、それ自体は評価ではない。
2. 「ツールの誤りを検出する手段(TD)」を主張するには、検出内容と負テストの対応表(検出する誤りの一覧 × テスト名 × 結果)が検証証拠として必要。evidence/ に無い。coverage.md は行カバレッジの数値のみ。
3. ツールの検証報告(バージョン、テスト環境、結果の記録)、構成管理、既知の異常のリスト、バージョンアップ時の再検証手順が無い。
4. 利用手引きの制約(「ツールが保証しない範囲」)は文書にあるが、ツールの出力(レポート・CSV)側に常に付くわけではない。レポートの先頭に 1 行の免責があり、「エラー 0」の表示は「このツールが検査する範囲で」とは限定されない。
5. AI 支援の扱い: 提案→承認、提供元・提案者・承認者の記録は評価できる。ただし AI 由来の要素を後から識別できないこと、承認者分離が認証設定時のみ有効なことが、独立レビューの根拠として弱い。
6. 安全分析の内容そのもの(サンプルの HARA・FSR・FTA・分解、AP 表、独立性の根拠の妥当性)は、実在の専門家による確認が必要。

**アセッサが実装面でも受け入れない点**: ①意図機能・安全機構の ASIL が検証されないこと、②FMEA-MSR の集計・SPFM/LFM/PMHF が無いこと、③FMEA の 7 ステップがワークフローとして管理されないこと、④FMEA の重大度と HARA の整合が見られないこと、⑤FTA が安全目標・FTTI・安全機構と結ばれていないこと、⑥「整合」(パズルビューの緑)が「検査した範囲で指摘なし」に過ぎないこと(文書化済みだが、画面表示だけでは区別されない)。

## 判定

ラウンド 3 の最重大の欠陥(R3-1)は、実コード・実 API の両方で修正を確認した。ASIL 継承の中核(安全要求)については、今回の探索で新たな抜け道を見つけられなかった。それでも、**3 項目とも合否点が 90 に届かない**(A1 85、B1 86、C1 89)。最大の理由は、(a) 同じ「ASIL の黙った引き下げ」が意図機能・安全機構の側に残ること(R4-1)、(b) AI 提案のゲートが評価値の引き下げを通すこと(R4-2)、(c) 7 ステップ・MSR の集計・SPFM/LFM/PMHF など機能の欠落、(d) ISO 26262-8 の証拠(負テスト対応表・使用ケース表・検証報告)の欠落である。修正 1〜3 は小さく、これが済めば B1 は 90 前後、C1 は 88〜90、A1 は 82〜84 まで戻る見込み。A1 を 90 以上の合否点にするには、7 ステップか MSR/SPFM の少なくとも一方の実装が要る。
