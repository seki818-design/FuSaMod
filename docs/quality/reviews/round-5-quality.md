### 2.2 `FUSAMOD_TRUST_PROXY`(**機能していない**)

| 設定 | `X-Forwarded-For: 9.9.9.9` を付けて認証失敗を発生させたときの、監査ログ上の接続元 |
|---|---|
| 未設定 | 127.0.0.1(正しい。信頼しない) |
| `true` | **127.0.0.1**(期待は 9.9.9.9) |
| `1` | **127.0.0.1** |
| `2` | **127.0.0.1** |
| `10.0.0.5` | 起動失敗(`parseTrustProxy` が拒否。仕様どおり) |

原因: `apps/server/src/config.ts` の `parseTrustProxy` が、`"true"` を**数値 1**に変換する。Fastify 5.12.5 では、`trustProxy: true`(真偽値)なら XFF が使われるが、`trustProxy: 1`(数値)では**使われない**ことを、Fastify 単体の試験(`inject` で 4 つの設定 × 3 つの XFF)で確認した(真偽値は `ip: 9.9.9.9`、数値 1/2/3 は常に `ip: 10.0.0.1` のソケット側)。
影響: リバースプロキシ背後で設定しても、全員が同じ IP と見なされ、認証失敗の制限(10 回/分)が全員で共有され、監査の `ip` は常にプロキシの IP になる。**R2〜R4 の 3 回続けて指摘した問題が、「対応済み」と書かれたまま実際には直っていない。** `apps/server/test` に `trustProxy`/`forwarded` を含むテストは 0 件(`grep` で確認)。`docs/security.md`・`.env.example` は「true で X-Forwarded-For を使う」と説明しており、記述が実装と食い違う。
副次: 設定しない既定は安全側(XFF を信頼しない)。なお、真偽値の `true` を直に渡す修正にすると、直接公開 + `TRUST_PROXY` で XFF を偽装されて制限を回避できる性質があるので、`docs/security.md` に「プロキシが XFF を上書き/付加し、サーバーがプロキシ経由でしか到達できない構成でのみ設定する」と明記が要る。

## 4. 項目別レビュー

### B6. セキュリティ — 採点 80 / 外部確認待ち減点 6(合否点 86)

**確認できた良い点(実測)**: 認証の迂回なし(31,504 件の変形、実 HTTP)。viewer の書き込みの全拒否(メソッド上書きヘッダを含む)。`docs/security.md`(脅威モデル)の新設。認証失敗の監査(連鎖つき、増加は有界)。AI のリスク低下に対する確認(409 → 確認)と来歴。`aiChanges` の削除・書き換えの 422。パストラバーサル、`.strict()`、定数時間のトークン比較、依存の脆弱性 0 件。

減点理由
1. **`FUSAMOD_TRUST_PROXY` が機能しない**(2.2)。R2〜R4 の 3 回の指摘に対して「修正済み」と書きながら、実測で効果がなく、テストも無い。文書が実装と食い違う。
2. **`aiChanges` の追記のみが復元で迂回される**(2.5)。また偽の来歴を追記できる。「来歴の改ざん防止」の主張に届かない。
3. **エクスポートで JVM を無制限に起動**(viewer でも可)、タイムアウトで JVM が止まらない(2.3)。低権限の利用者による資源枯渇。
