| 構文・参照エラー・重複名(`bad`) | JSON・XMI とも **409**(約 0.1 秒、本文は日本語の理由。内部パスなし) | X2 修正を確認 |

### 新規欠陥(実装)

**[N1 高] 解析タイムアウト直後のリクエストでサーバーがクラッシュする(DoS)。**
`apps/server/src/sysml/java-service.ts`: タイムアウト時に `this.kill()`(SIGKILL)するが、`this.proc` / `this.ready` は `exit` イベントまで残る。その間に来た次のリクエストが
死んだプロセスの `proc.stdin.write()` を行い、`stdin` に `error` リスナーが無いため `Error: write EPIPE` が未処理例外になり、Node が終了する(`server2.log` / `server.log` で確認)。
編集者権限があれば `PUT /model` で 236KB(上限 2MB 未満)のモデルを保存し、続けて任意のリクエストを送るだけで落とせる。エクスポートの堅牢化(ラウンド 5 の主題)の外側だが、エクスポートの 409 経路から再現した。
また、**タイムアウトが「モデルの誤り(409)」として返る**(利用者に誤った原因を示す)。3,000 part 規模で 60 秒を超える解析性能そのものも、実務のモデル規模では問題になる(B2/B5 の領域)。

**[N2 中・トレーサビリティの誤り] `requirement def` の型付き使用の入れ子要求への `satisfy` がインスタンスに付かない。**
`requirement r1 : ReqD;` に対し `satisfy r1.subB.deep by v.front.brake;` は、公式抽出器が要求側を `Root::ReqD::subB::deep`(定義側)に解決する。`by` 側は `byChain` で経路が運ばれるが、**要求側の経路は運ばれない**ため、
`Root::r1::subB::deep` に付かず、定義側の要求(幽霊要求として表示されない)に付いて消える。実測: `trace.cells` に `r1::subB::deep → v::front::brake` が無く、`deep` は親 `r1` から継承した `tap` にだけ紐づく。
指摘(警告・`SATISFY_UNRESOLVED`)も出ない。`r2.n1.n2`(入れ子の通常の requirement)は正しく解決される。ADR-0008 の「入れ子 requirement」「requirement def 展開」の規約と矛盾する黙った誤りで、`brake` の要求カバレッジと影響分析が誤る。
(`tools/sysml-check/SysmlExtract.java` に要求側の連鎖を出し、`packages/sysml-graph/src/expand.ts` で解決する必要がある。)

**[N3 中] 多重度の警告に抜けがある。**
- 警告される: `[0..*]` `[1..*]` `[*]` `[3]` `[2..5]` `[0..2]` `[2..2]`(`Q::s` のように、型の定義内メンバーも)。**ラウンド 5 の C2-O1(上限なし)は修正を確認**。
- **警告されない**: `[n]`(属性 `n = 3` を参照する式。実際は 3 個)、`[0]`(0 個のはずが 1 個扱い)、`[0..1]` / `[0..*]` の**下限 0**(任意の部分を必須として扱う。SPOF 判定を誤らせうる)。
- 同じ定義内メンバーの警告が、定義を使う使用ごとに繰り返される(`M::Q::s` が 2 回)。インスタンス経路が出ず、どの使用の話か分からない。
- ADR-0008 は「上限が 1 を超える」としか書かず、`*`・下限・式の扱いが未記述(前回の指摘も未修正)。

**[N4 低] SCDL エレメント ID の不安定(C2-O2)は未修正。** `package A0 { part v … }` を足すと `Root::v` が `v#2` → `v#3`、`Other::v` が `v` → `v#2` にずれる(実測)。
ADR-0007 の追補は「同名の根を足すと割り当てが変わりうる」と**訂正済み**(文書は正確になった)が、実装は変わらない。衝突自体は正しく回避される(`n3`: `x`/`x#2`/`x#2@E`/`y@E` を含めても重複 0)。
`modelRef`(完全修飾名)での追跡は可能。

**[N5 低] ADR-0008 の記述が古い。** `docs/adr/0008-derive-nets-from-sysml.md` 72 行目は「標準 JSON、XMI は**未対応**」とあり、ADR-0009 / 実装(書き出し済み)と矛盾する。

### 変換経路の品質(未修正のまま)

- **X1**: ev-powertrain の XMI に `href="model.sysml#|0"` … の**解決できないプロキシ参照が 9 箇所**。JSON も `Type` / `Namespace` が名前なし(4 + 2 要素)で `isLibraryElement` は全要素 false。`Real` 型の属性は受け側で型不明になる。
- **X4**: 同じプロジェクトを 2 回エクスポートして、XMI の `xmi:id` 225 件の共通は 0。FuSaMod の ID(完全修飾名)との対応表も `qualifiedName` も無い。
- 応答文書は X1/X4 を「公式変換器の挙動で、本ツールでは直せない」とするが、**検証されていない主張**。同じ `libs`/`sysml.library` を `PilotCheck` は読み込んでおり(`run.sh`)、ID は変換後処理(完全修飾名からの UUID v5 への付け替え)で決定的にできる。「直せない」ではなく「未着手」。
- JSON は `Commit`/`DataVersion` で包まれていない(ADR-0009 に明記済み)。API サーバーや他ツールへの実投入は未確認(環境にない)。
- 取り込み(JSON / XMI / API)はない。SCDL ビューの `export/scdl.sysml` は取り込み(`importSysml`)と往復で一致するが、HTTP の取り込み口はない。
- `scdl.sysml` の `modelRef` は**文字列**で、元モデルへの SysML 上の参照(`ReferenceSubsetting` / `allocate` など)ではない。構造を複製した別のビューであり、MBSE の意味でのトレースは文字列の一致に頼る。
- `sweepConvertTemp(0)`(起動時)は `fusamod-convert-*` を**全部**消す。同じホストで別インスタンスが変換中なら、その一時ファイルを消してしまう(低頻度)。

### ADR-0009 の正直さ

- 良い: 書き出しのみ、取り込み・API なし、他ツールで未確認、X1(ライブラリ)・X2(409/422)・X4(ID)・`Commit` なし・同時 2 件/待ち 4 件を明記。実測と一致(X2/X3 の挙動、429、ID 非決定、プロキシ参照)。
- 不足: X3 が「単位式など」としか書かず、**本ツール自身の SCDL ステレオタイプ(`import SCDL::*`)を含むモデルで JSON が作れない**ことが書かれていない(`examples/sysml/all-stereotypes.sysml` で再現。XMI は成功)。
  タイムアウト(503)、巨大モデルの扱い、親プロセス死亡時の変換器の残存も未記載。「方針: 公式 API を利用する形で追加」は、実装が「.sysml → 変換器」の一方向である点とずれたまま。
- 誤り: X1/X4 を「本ツールでは直せない」とする断定(上記)。

## 2. 定義・再定義・特殊化・requirement def・SCDL ID(実測の総括)

確認できた長所:
- `n1`: `BigPack :> Pack { part :>> cells { part tap; } part :>> bms { part mon2; } part extra : Cell; }` と `v : Veh { part :>> front { part brake; } }` で `v::pack::cells::tap`、`v::pack::bms::mon2`、`v::pack::extra`、`v::front::brake`、2 本の車軸(`front`/`rear`)が正しく展開。`v2 : Veh` も別に展開。
- `requirement def ReqD` の型付き使用 `r1` は、本文と入れ子(`subA` `subB` `subB::deep`)を複製。定義側の幽霊要求なし。入れ子 `r2.n1.n2` の `satisfy` は正しい(明示があれば親の継承より優先)。インスタンス経路 `satisfy … by v.pack.cells.tap` / `v2.rear.hub` は正しい 1 つのインスタンスに解決。
- 影響分析(`impactOfRequirementChange` を直接呼出し): 下位(入れ子)・上位(`upstream`)が方向つき。`r2` の影響範囲は `v::pack` とその下位 7 要素、`r2::n1::n2` は `v2::rear::hub` のみ。
- SCDL: 同名の根・特殊文字の ID 割当ては一意(22/22、`n3` も重複 0)。`export/scdl.sysml` は `PilotCheck` でエラー・警告ゼロ(ev-powertrain、`n2` の日本語・`'a/b'`・`q"uote`・`x#2`・`IF-1@E`・同名 `Dup` ×3 を含む)。`importSysml` → `exportSysml` はパッケージ名以外が完全一致。

欠陥は上記 N2〜N4。加えて、`part a { part b }` と `part 'a/b'` の ID が `/` で曖昧(`a/b#2`)な点は残る(軽微)。

## 4. 実務の MBSE 担当者がまだ拒否する点

実装の欠陥(直せる):
1. 巨大モデルの解析タイムアウト直後に、サーバーが `EPIPE` で落ちる(N1)。タイムアウトが「モデルの誤り」(409)になる。
2. 標準 JSON/XMI の標準ライブラリ参照が空要素・プロキシ(X1)。`elementId` が毎回変わる(X4)。SCDL 注釈付きモデルが JSON にならない(X3)。
3. `requirement def` の型付き使用の入れ子要求への `satisfy` が、黙ってトレースから落ちる(N2)。
4. 多重度 `[n]`・`[0]`・下限 0 が無警告(N3)。同名の根の SCDL ID がパッケージ追加でずれる(N4)。
5. ADR-0008 に「標準形式は未対応」の古い記述(N5)。ADR-0009 の X3 に SCDL import の記載なし。

範囲の問題(ADR に記載済みの未対応):
- SysML v2 API(REST)接続、JSON/XMI の取り込み、往復。`Commit` で包んだ投入形式。他ツールでの読み込み確認。
- port / connection / interface / flow / state / allocation を解析に使えない。`verify` / `derive` / `refine` がない。
- SCDL ステレオタイプは独自のメタデータ定義で、他ツールでの解釈は未確認。

## 5. 優先修正(ファイル単位)

1. `apps/server/src/sysml/java-service.ts`(N1): `proc.stdin.on("error", …)` を付け、タイムアウト・`kill()` 時に即座に `reset()`(`this.proc`/`this.ready` を破棄)して、死んだプロセスへ書かない。タイムアウトは 409 ではなく 503/504 で返す(`app.ts` の `requireAnalysis`/エクスポートの分類)。回帰テスト: 代役プロセスが応答せずタイムアウト → 直後のリクエストが成功し、プロセスが落ちないこと。
2. `tools/sysml-check/SysmlExtract.java` と `packages/sysml-graph/src/expand.ts`(N2): `satisfy` の**要求側**の連鎖(`r1.subB.deep`)を `byChain` と同様に出力し、型付き requirement のインスタンスに付ける。解決できないときは `SATISFY_UNRESOLVED`。回帰: `requirement r1 : ReqD; satisfy r1.subB.deep by v.front.brake;` で `r1::subB::deep → v::front::brake`。
3. `packages/sysml-graph/src/expand.ts`、`docs/adr/0008`(N3): `[n]`(式)・`[0]`・下限 0 を警告(または扱いを仕様化)。警告にインスタンス経路を付け、使用ごとの重複を整理。ADR に `*`・下限・式の扱いを明記。
4. `tools/sysml-check/convert.sh`、`apps/server/src/sysml/convert.ts`(X1/X4): `sysml.library` と `SCDL.sysml` をリソースセットに載せる(`PilotCheck` と同様)。変換後に `elementId` を完全修飾名からの決定的な UUID(v5)に付け替え、`qualifiedName` との対応表を付ける。SCDL 注釈付きモデルの JSON 化(NPE の回避)を調べる。
5. `packages/analysis/src/scdl-map.ts`(N4): 同名の根の ID にパッケージ名由来の安定な接尾辞を使い、パッケージ追加で既存 ID がずれないようにする(または、ずれる仕様を維持して `modelRef` での追跡を UI で明示)。
6. `docs/adr/0008`(72 行目)・`docs/adr/0009`: 「標準形式は未対応」を訂正。ADR-0009 の X3 に「`import SCDL::*` を含むモデルは JSON 不可」、タイムアウト・巨大モデル・「直せない」の断定の見直しを記載。
7. `apps/server/src/sysml/convert.ts`: 親プロセスの死亡で変換器を止める(`prlimit`/`timeout` コマンドのラップ、またはハートビート)。起動時の全削除(`sweepConvertTemp(0)`)を、別インスタンスと衝突しない名前(PID 入り)にする。
8. 中長期: JSON/XMI の取り込み、SysML v2 API クライアント、`verify`/`derive`/`refine` と port/connection/allocation の導出、`modelRef` を SysML 上の参照にする、他ツールでの実読込テスト、jar の第三者ライセンス棚卸し。
