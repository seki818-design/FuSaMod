## 1. SPFM / LFM の検証(本ラウンドの新規)

### 1.1 式・定義・目標値(ISO 26262-5 との照合、自分の知識に基づく)
| 項目 | 実装 | 判定 |
|---|---|---|
| SPFM = 1 − Σ(λSPF+λRF)/Σλ | `1 − single/total`。single = Σ fit·(1−safe)·(1−dcSpfRf) | 式の形は正しい。ただし下記の差異あり |
| LFM = 1 − Σλ潜在 /(Σλ − Σ(λSPF+λRF)) | `1 − latent/(total − single)` | 式の形は正しい |
| 目標値 B 90/60、C 97/80、D 99/90 % | `HW_TARGETS` のとおり | 正しい。ただし、ASIL B の値は標準では「推奨(目標値は参考)」の位置づけで、C/D と同じ「エラー」にしてよいかは組織の判断(出力にその注記が無い)。A と QM は目標なし(正しい) |
| 手計算との一致 | `hwmetrics.test.ts` で確認。デモ値は SPFM 99.50 %、LFM 95.3 %(私の手計算と一致) | 確認 |

保守側(安全側)の簡略化で、標準そのままではない点:
- 標準の Σλ は安全な故障(λS)を含む。本実装は `safeFraction` を分母から先に除くので、同じ入力なら標準より低い値(保守側)になる。文書に書かれていない。
- 標準の λMPF,latent は「検出も認知もされない」多重故障のみ。本実装は認知(perceived)の割合を持たず、`1 − dcLatent` を全部潜在とみなす(保守側)。
- λSPF(安全機構なし)と λRF(機構あり・残存)を分けず、`λ(1−DC)` に一本化している。数値は同じになるが、報告書に SPF と RF の内訳が出ない(アセッサは FMEDA の内訳を見る)。

### 1.2 入力の扱い(モデル化)と、誤解を招く点 — 実行で確認
1. **ASIL B 以上の安全目標があっても、`hardwareFailureModes` が無い/空でも指摘ゼロ**(`delete safety.hardwareFailureModes` を `PUT` → 200、新規指摘 0、画面は「故障率を入れると算出されます」の灰色の注記のみ)。証拠の欠落が「適合」と区別されない。アセッサは「ASIL D の SPFM の証拠が無い」を最重大の指摘にする。
2. **全モードの `safeFraction` = 1、または fit = 0 では total = 0 となり、`spfm`/`lfm` は undefined、指摘ゼロ**(実行確認)。「未算出」が「合格」に見える。
3. **分類を利用者が選べて、検査は無い**: 単一点故障のモード(1000 FIT)を `type: "multiple"`、`dcLatent: 1` に付け替えると、SPFM 99.9999 %・LFM 100 %、指摘ゼロ(実行確認)。`type` と `dcLatent` の根拠欄(理由・出典)が無い。`safeFraction` も 0.9999999 のように根拠なしで入力でき、分母から除かれる。文書はこの限界を書いている(「分類の妥当性は検査しない」)が、**根拠の記録欄すら無い**ので、アセッサは成果物として受け取れない。
4. **安全機構との未連携**: `dcSpfRf` は `mechanisms[].diagnosticCoverage`(high/medium)や `coversFailureIds` と照合されない。デモは機構 SM-1 が `medium` なのに、HW-2 は `dcSpfRf: 0.995`(高カバレッジ以上)。標準の Annex D の「DC の根拠(高 99 %、中 90 %、低 60 %)」とも、`MECH_DC_D_MISMATCH` とも無関係に通る。`dcSpfRf: 1`(残存ゼロ)も許される。
5. **ASIL の決め方が粗い**: 安全目標のうち最大の ASIL 1 つで全モードを評価する(保守側だが、標準は安全目標ごと)。故障モードと安全目標の対応が無いので、ASIL A の目標に関わるだけの要素にも D の目標を課す一方、目標ごとの SPFM は出せない。
6. **構造の網羅性なし**: `elementId` は任意で、存在確認のみ。ハードウェア要素のうち故障率を持たないもの(漏れ)を検出しない。故障率の出典(FMEDA、SN 29500、IEC TR 62380 など)の欄も無い。
7. **潜在故障の診断間隔・被曝時間なし、PMHF なし**: 文書は正直に書いている(下記 3)。ASIL D の確率的な指標(PMHF < 10 FIT)が無いので、「ハードウェアの評価が済んだ」とは言えない。

### 1.3 変更管理(`riskChanges` の hardware 分類)— 実行で確認
- 検出: 故障モードの削除(`lowersRisk`)、`dcSpfRf` 0.97 → 1(`lowersRisk`)、`single` → `multiple`(`lowersRisk`)、`hardwareFailureModes` ごとの削除。
- **見逃し / 誤分類**:
  - **新しい故障モードの追加は差分に出ない**(`fit: 50000, safeFraction: 1` の単一点故障の追加、`fit: 5000, type: "multiple", dcLatent: 1` の追加は `diff=none`)。大きな無害な故障率を足すと、SPFM が上がる(分母が増える)。
  - **`fit` の増加を非リスク低下(`lowersRisk: false`)に分類**。診断カバレッジが高いモードの fit を増やすと SPFM は上がる(HW-2 を 50 → 5000 で実行確認: 差分は出るが `lowersRisk=0`)。方向の単純化が誤り。
  - **`undefined` → 値の変更を `lowersRisk` にしない**(`safeFraction` を未設定から 0.99 にする、`dcSpfRf` を未設定から追加する、は `lowers=0`)。
  - `elementId`・`name` の変更は差分に出ない(根拠の欄が無いので当然)。
- 結論: 文書の「ハードウェア故障率の低下を `riskChanges` が分類する」(negative-tests の追加表)は、**範囲が限定された記述としては真だが、SPFM を良く見せる主要な操作(無害な故障モードの追加)を逃す**。

### 1.4 総合(SPFM/LFM)
計算式と目標値は正しく、保守側に倒れている。A1 のチェックリストに近づいた(+3)。ただし、「適合の証拠」として使うと、**欠落の無指摘、分類の自由、根拠欄なし、安全機構との未連携**により、false assurance の経路になる。ISO 26262-5 で言う「メトリクスの算出」ではなく、「利用者が入れた分類に対する算術」であり、その位置づけは文書に正確に書かれている(1.2 の 1, 2, 4, 6 は書かれていない)。

2. 検証報告が無い(版・日時・環境・合否の記録を自動生成する仕組みがない)。

**アセッサが実装面でも受け入れない点(ISO 26262-5 / -9 / -4 の観点)**
