## 2. 第 7 回の指摘の再検証

### 2.1 JVM の世代競合(`java-service.ts`)— 修正を確認

コードは、各ハンドラ(`error`・`exit`・stdin の `error`・`rl.line`)の先頭で `this.proc !== proc` なら何もせず、`kill()` が先に `this.proc` を切り離す構造に変わっている(`java-service.ts:70-90, 125-131`)。実測は次のとおり。

| 試験(バンドル版・実 HTTP) | 結果 |
|---|---|
| R7 の再現手順: 重いモデル A(`m_flat_15000`、1.0 MB)→ 1 秒後に重いモデル B(`m_conn_8000`)。3 回繰り返す | A: 200(66〜74 秒、タイムアウト)。B: 200(131〜139 秒 = A の終了待ち + 自身の 60 秒のタイムアウト)。**3 回とも、その後に残る JVM は 0、または 1 つ**(孤児なし)。`/api/health` は 200 |
| タイムアウト直後の通常モデルの解析 | `modelOk:true`(105 ms / 再起動は約 6.5 秒)。「Java 21 が必要」という誤った縮退メッセージは出ない |
| 解析の途中で JVM を `kill -9` → 直後に未キャッシュの 2 モデルを同時に解析(2 回) | 重いモデルは 200(`SysML サービスが終了しました`、4〜5 秒)、後続の 2 件は成功(約 6.5 秒)。JVM は 1 つだけ |

### 2.2 待ちの上限(`maxQueue` → 429)

- `POST /analyze`(viewer)を重いモデルで 11 件同時: **3 件が 0.2〜0.3 秒で拒否**(実行 1 + 待ち 7 = 8 件を受理)。残り 8 件は直列に 67 / 137 / 205 / 274 秒で完了または(私の 300 秒の待ちで)中断。
- **ただし `/analyze` の拒否は HTTP 200 + `{"modelOk":false,"sysmlError":"SysML の解析待ちが多すぎます…"}`**。429 になるのはエクスポートと AI のみ(`app.ts:286-291` の `analysisUnavailable`)。`view()`(`app.ts:185-198`)は `sysmlFailure` を応答に含めないため、クライアントは文言でしか種別を判定できない。
- 利用者ごとの上限が無い。1 人(viewer でも可)が 8 件を埋めると、他の全員の解析が最大 8 × 60 秒待たされる。
- 私の側のクライアントが 300 秒で切断した後も、サーバー側は待ち行列の要求を処理し続け、JVM を再起動し続けた(切断で処理を取り消さない)。

### 2.3 タイムアウト / 停止 / 多忙 / モデルの誤りの分類 — エクスポートと AI は一貫

重いモデルを保存したプロジェクトで実測した。

| 経路 | 結果 |
|---|---|
| `fmea.csv` / `report.md` / `scdl.sysml` / `model.json` / `trace.csv`(同時発行) | すべて **504**(67 / 67 / 134 / 203 / 276 秒。直列に並ぶ) |
| `ai/chat` | **504**(72 秒) |
| 構文エラーのモデルの `model.json`(同時 10 回) | **409**(モデルの誤り)。0.1〜0.3 秒 |
| 単位系モデルの `model.json` を 10 件同時 | 6 件受理(2 実行 + 4 待ち、20〜61 秒)、**4 件が 429**(0.01 秒) |
| `GET /api/projects/<重いモデル>`(viewer) | 200(60 秒以上かけて `sysmlError` つき) |

→ 504 / 429 / 409 は一貫して使われている。ただし**失敗が記憶されない**ため、同じ重いモデルへの要求は毎回 60 秒 JVM を占有する(上記の 5 件が直列に 67〜276 秒)。保存済みのモデルが重くなった場合、そのプロジェクトを開くだけ(`GET`)で全利用者の解析が止まる。

### 2.4 起動時の一時ディレクトリ掃除

- 掃除の対象は共有の `/tmp` 直下から `tmpdir()/fusamod-<uid>/convert`(0700)に変わった。他ユーザーの物を消す問題は**解消**(コード確認 + `fusamod-0/convert` 配下のみの動作を確認)。
- **残る問題(新規・低〜中、再現済み)**: `main.ts:44` の `sweepConvertTemp(0)` は、**同じユーザー・同じ一時領域**を使う別インスタンスの作業ディレクトリも無条件に消す。再現: `TMPDIR` をスクラッチ領域に固定したサーバー A で単位つきモデルの `model.json` を要求(約 15 秒)→ 7 秒後に同じ `TMPDIR` で サーバー B を起動 → A の要求が **422(「モデルの誤り、または変換器が対応していない記述」)** で失敗。偽のディレクトリ `fusamod-convert-fake` を置いて B を起動すると消える。再起動(1 インスタンス)や別ユーザーなら問題にならないが、検証用インスタンスや複数インスタンス運用では、環境の失敗がモデルの誤りとして報告される。
- `/tmp/fusamod-<uid>` は予測可能な名前で、`mkdir -p` は所有者を確認しない(コード確認のみ。未実測)。別ユーザーが先に作ると、この利用者の変換が失敗しうる(DoS、低)。
