## 2. 新たに見つかった欠陥・残った欠陥(再現手順つき)

### 2.1 同じ文字数の書き換えは、差分にも監査にも出ない(重要度: 高。応答書の「必ず記録」が偽)

`differ().text()` は、`(記述あり N 文字)` という**長さの表示文字列**同士を `push()` の `from !== to` で比べる。文字数が同じだと表示文字列が等しく、記録されない。実行結果(いずれも `riskChanges` = `NO DIFF`):

- 分解の独立性の根拠 `DFA-PT-001(独立電源・独立クロック・別マイコン)` → `DFA-PT-002(…)`(文書番号だけの差し替え。**最も自然な編集**)
- ペアの `independence` の `独立` → `従属`(意味が正反対でも文字数が同じ)
- FMEA リンクの `detectionControl` の `独立監視` → `なし　　`
- HW の `rationale` の `デモ` → `ＸＹ`

API でも確認した: `PUT /api/projects/ev-powertrain/safety` で独立性の根拠の `PT-001` → `PT-002` → 200、`safety.diff` の監査イベントは **0 件**。AI の適用でも同様で、`setLinkRatings` で `detectionControl` を同じ長さに書き換える提案は、確認なしで 200、`aiChanges[].changes` は `[]`(提案が何を変えたかの来歴が空)。応答書とテスト(`ai.test.ts` の新テストは長さの違う例のみ)は、この穴を捕まえていない。修正は、表示文字列でなく本文(またはそのハッシュ)の不一致で記録すること(数行)。

### 2.2 差分の対象外の項目(重要度: 中。応答書の「HARA の根拠」が偽)

`riskChanges` は次を一切見ない(実行で `NO DIFF`、`PUT /safety` でも監査なし): HARA 事象の `rationale`・`hazard`・`situation`、安全目標の `text`・`safeState`。HARA の S/E/C・ASIL・FTTI は見る(確認)。同様に、機構の `coversFailureIds` を同数で入れ替える、機構や HW 故障モードの `elementId` を移す、ペアの機能/機構を付け替える(新規の QM 機構への付け替えでも `lowersRisk` は「QM の追加」の 1 件のみ)、分解の `parentRequirementId`・`childRequirementIds` を変える(この変更は解析側がエラーにする)、FTA のゲートの入力を同数で入れ替える、AND ゲートに入力を足す(頂上事象を起きにくくする主張。現在は `lowersRisk` でない)は、差分に出ない。

### 2.3 評価できていない目標があっても、画面の合算 SPFM/LFM は緑(重要度: 中。誤解を招く表示)

再現(実サーバー + Playwright): デモのコピーで (a) 全故障モードの `goalIds` を `["SG-2"]`(ASIL A)に付け替える、または (b) SG-3(ASIL C)と事象・要求を足して故障モードは SG-1 のみ。どちらも画面の「ハードウェアメトリクス」は `SPFM 99.35%(目標 99.00%)`・`LFM 90.59%(目標 90.00%)` が**緑(`badge ok`)**。(a) では ASIL D の SG-1 に関係する故障モードが 0 件(警告 `HW_METRICS_MISSING@SG-1` は「問題」タブにだけある)。注記は「全故障モードの合算。安全目標ごとの判定は『問題』タブ」と小さく付いたが、緑のバッジは ASIL D の目標が未評価であることを隠す。`perGoalNg`(エラー)は黄色にするが、`HW_METRICS_MISSING`(警告)では色が変わらない。なお故障率 0 の場合の「—(算出不可)」の黄色表示は確認(修正済み)。
