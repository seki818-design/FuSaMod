## 2. 第 8 回の指摘の実測

試験用の重いモデル: 12,000 段の特化(`part def P0; part def P1 :> P0; … P12000 :> P11999;`、約 326 KB)。

### 2.1 重い解析のタイムアウトと再解析の抑制 — 逐次は直った、同時は直っていない

| 試験(バンドル版・実 HTTP) | 結果 |
|---|---|
| 重いモデルの `GET export/fmea.csv` を**逐次 3 回** | 504 (66.7 秒) → 504 (**0.055 秒**) → 504 (**0.059 秒**)。記憶が効き、2 回目以降は JVM を使わない。viewer の `GET /api/projects/heavy` と `POST /analyze` も 0.03〜0.08 秒で、`sysmlFailure:"timeout"` と「しばらく再解析しません」の文言つき |
| サーバーを再起動(記憶を消す)して、同じ重いモデルの `GET export/fmea.csv` を**同時 5 件** | すべて 504 だが、完了は **74 / 146 / 219 / 288 / 355 秒**。**5 件とも JVM を約 70 秒ずつ占有**(直列)。**記憶が効かない** |
| viewer が、**1 文字だけ違う**重いモデル 3 件を `/analyze` に同時送信 → 3 秒後に編集者が自明な小さいモデル(2 要素)を `/analyze` | viewer 3 件は 67 / 134 / 200 秒。**編集者の自明な解析は 203 秒後に成功** |
| 同じく viewer の `/analyze` で別の重いモデル 11 件を同時 | 3 件が即時に `sysmlFailure:"busy"`(HTTP 200)、残り 8 件が直列に受理される |

原因(コード確認): `services.ts` の記憶(`timedOut`)は `sysml.analyze()` を呼ぶ**前**に1 回見るだけで、キューで待っている間・待ちから出た後には再確認しない。同じハッシュの実行中の要求を 1 つにまとめる処理(in-flight の統合)もない。記憶はハッシュ単位なので、**中身を変えるだけで回避できる**(viewer でも可)。利用者ごとの待ち上限、viewer のモデルサイズ上限、切断時の取り消しはいずれも R8 の指摘のまま未実装。

→ R8 の「重いプロジェクトを開くたびに毎回 60 秒」は**逐次の場合に限り**解消。「利用者が共有 JVM を長時間占有できる」は**解消していない**(B2 の主因)。

### 2.2 `sysmlFailure`(機械可読な値)— 修正を確認(一部のみ)

`GET /api/projects/:id` と `POST /analyze` の応答に `sysmlFailure` が入る。実測した値: `timeout`(上記)、`busy`(11 件同時)、`unavailable`(解析中に JVM を `kill -9` → `SysML サービスが終了しました`、`sysmlFailure:"unavailable"`)。次回の通常のプロジェクトの読み込みは成功した。
残る点: HTTP 状態は 200 のまま(エクスポート・AI は 504/429/503)。**Web UI は `sysmlFailure` を使わず**(`api.ts` に型があるだけ)、従来どおり `sysmlError` の文言を表示するだけ。**サーバーの HTTP 層で `sysmlFailure` を検査するテストが無い**(`apps/server/test` に 0 件。`AnalysisService` の単体テストのみ)。

### 2.3 SIGTERM が速く終わるか — **効いていない**

| 状況 | 終了までの時間 |
|---|---|
| 待機中(解析なし) | 2.1 秒 |
| viewer の `/analyze`(重いモデル)が **JVM 実行中**(要求の 6 秒後) | **55.9 秒**(クライアントには 60 秒後に 200 が返る) |
| 重い要求を 11 件投入した直後(JVM 起動中) | 8.9 秒 |

R8 の対応表の「先に Java を止めてから HTTP を閉じる」は、実行中の解析には効かない。原因: `JavaSysmlService.close()` は `kill()` を呼び、`kill()` は先に `this.proc` を切り離す(`java-service.ts:125-130`)。その後に来る `exit` イベントは `stale()`(`:70-76`)で無視されるため、`failPending()` が呼ばれず、**進行中の要求が拒否されない**。60 秒のタイムアウトまで `app.close()` が待つ。`docker stop`(10 秒)や systemd では強制終了になりうる。孤児 JVM は残らない(確認済み)。修正は `close()` で `failPending(new SysmlUnavailableError(…))` を呼ぶ 1 行で済む。回帰テストなし。

### 2.4 起動時の掃除 — 修正を確認

`TMPDIR` をスクラッチ領域に固定したサーバー A で単位つきモデル(`ISQ`/`SI` を import、`[kg]` `[kW]`)の `model.json` を要求(**27 秒**。他の担当の負荷下)。変換が走っている間にサーバー B を同じ `TMPDIR` で起動 → **A は 200 で完了**(R8 は 422)。10 分より新しい偽ディレクトリ(`fusamod-convert-fresh`)は残り、20 分前の偽ディレクトリ(`fusamod-convert-old`)だけが消え、`fusamod-convert-` で始まらない `other-keep` は残った。`fusamod-0` と `convert` は 0700。
残る点(コード確認のみ): `mkdir -p` 後に `/tmp/fusamod-<uid>` の所有者を確認しない(別ユーザーが先に作ると DoS、低)。
