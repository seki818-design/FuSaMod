# ツール分類の提案(ISO 26262-8 第 11 章)

> 本書は**提案**であり、認定ではない。TCL の判定と受け入れは、利用組織の機能安全マネージャーが行う。

## ユースケースと分類(提案)

| # | ユースケース | 誤りの影響(TI) | 誤りの検出手段(TD) | 提案する TCL | 備考 |
|---|---|---|---|---|---|
| UC1 | FMEA / FTA / HARA / ASIL 分解の**作成・保存** | TI2(誤ったデータが安全分析の成果物になりうる) | 利用者のレビュー、整合性チェック(指摘タブ)、履歴・監査ログ | TCL2〜3(組織の手順でレビューするなら TD2) | 検出できる誤り/できない誤りは docs/safety-notes.md |
| UC2 | ASIL **決定**(HARA の S/E/C → ASIL) | TI2 | ISO 26262-3 Table 4 の全 80 通りの自動テスト、利用者のレビュー | TCL2(TD1〜2) | `packages/safety-core/test/hara-fta.test.ts` |
| UC3 | ASIL **分解・継承の検査** | TI2(検査漏れ) | 負テスト(わざと誤ったデータを与える) | TCL2〜3 | 下記の負テスト一覧 |
| UC4 | 最小カットセット・確率の上限 | TI2 | 完全でない結果は「不完全」と表示、利用者のレビュー | TCL2〜3 | 独立事象の仮定。PMHF ではない |
| UC5 | AI の提案 | TI2 | **承認が必須**、差分と来歴の記録、リスクを下げる変更の確認 | 提案は成果物にならない(承認後のデータの扱いは UC1) | |
| UC6 | SysML からの構造・機能ネットの導出 | TI2 | 未対応構成の警告、利用者のレビュー | TCL2〜3 | ADR-0008 |
| UC7 | 表示・エクスポート(CSV/レポート) | TI1〜2 | 利用者のレビュー | TCL1〜2 | 非公式 AP 表の明示 |

TI: ツールの誤りが安全関連の成果物に影響するか。TD: 誤りを防ぐ・検出する確信度(TD1 高 … TD3 低)。

## 検証(Tool Validation)の証拠として使えるもの
- 単体・結合テスト(`pnpm test`)、E2E(`pnpm e2e`)、カバレッジ(`pnpm coverage`)、公式 SysML 実装との結合(`pnpm test:integration`)。
- 負テストの一覧: [evidence/negative-tests.md](evidence/negative-tests.md)。
- 構成管理: Git の履歴、`pnpm-lock.yaml`、CI。
- **未整備**: 利用組織での使用条件の定義、使用中の不具合の記録と処置の手順、ツールのバージョン固定と変更管理の運用手順、実在の評価者によるレビュー。

## 検査が「通してしまう」領域（ラウンド 9 で明記）
負テストで確かめているのは「誤りを検出する」ことで、次は**検出できない**（人のレビューが必要）。
- 根拠文字列（独立性の根拠・HW の `rationale`）は、形式（長さ・文字の種類・後回しの表現）しか見ない。実在しない文書番号（例: `DFA-nonexistent-999`）は通る。
- 意図機能・安全機構を、ASIL の低い安全目標の要求へ付け替えて、ASIL も一緒に下げたデータそのものは、静的検査では矛盾にならない。**変更の検出（`riskChanges` の差分、承認時の確認、`safety.diff` の監査）で扱う**。差分は、記述の書き換え（同じ長さを含む）も内容の指紋つきで記録する。
- 故障率・分類・診断カバレッジの妥当性、AP 表の正式性、HARA の S/E/C の評価の妥当性。
- AI の適用（UC5）の監査: `ai.apply` に加えて、差分の概要を `safety.diff`（`via: "ai"`、リスク低下の件数、確認の有無）で残す。
