# 安全規格上の位置づけ・制限事項

## ツールの位置づけ(ISO 26262-8 第 11 章 ソフトウェアツールの信頼性評価)
本ツールは安全分析の**支援ツール**であり、成果物(FMEA・FTA・ASIL 判定)の最終責任は利用者にある。
- 想定利用ケース: 安全分析データの作成・整合性検査・可視化。ツールの出力は設計成果物へ入る(TI は 1 ではない可能性)。
- 誤りの検出手段(TD): 整合性チェック(指摘タブ)、HARA の ASIL 表の自動テスト、利用者によるレビュー。ただし**検出が確実とは主張しない**。
- 暫定の提案: TD2 以上を想定し、**組織の手順で ASIL 判定と FMEA の独立レビュー**を必ず行う。ツール認定(TCL 判定)は組織の安全マネージャーが実施すること。本リポジトリは認定の証拠を提供しない。
- 検証の根拠: ASIL 決定表・デコンポジション表・最小カットセット・AP 表検証のユニットテストと、公式 SysML 実装による結合テスト(`docs/quality/evidence/`)。

## 既知の制限
- AP(Action Priority)表は、**正式な表を同梱しない**(AIAG-VDA の表は著作物のため)。利用者が用意し、`compileApTable` が網羅性・重複・単調性を検証する。未設定時は RPN のみ表示。サンプルプロジェクト(`projects/ev-powertrain`)には、動作確認用の**非公式の玩具の表**(64 規則。正式な表との照合はしていない)が入っており、画面・CSV・レポートに「非公式」と明記される(`apTableSource`)。実際の分析には使わないこと。
- FTA: 故障ネットから導出するツリーは **OR ゲートのみ**(AND は保存したツリーで手で作る)。確率は独立事象を仮定する簡易な上限(Esary-Proschan)で、**潜在故障・被曝時間・診断カバレッジは扱わない**(PMHF の算出ではない)。共通原因故障は別途扱う。FTA と安全目標・FTTI の自動連携はない。
- ASIL デコンポジションの独立性は「根拠の記録と有無の検査」までで、独立性の妥当性そのものは判定しない。
- SCDL は v1.6.0 の概念を SysML v2 のステレオタイプで表現した独自写像であり、ASAM の公式ツールとの相互運用は確認していない。
- AI 提案は誤りうる。承認前に必ず人が確認する。
- 実際の利用者による使い勝手の評価、および規格適合の第三者確認は未実施。

## ツールが検出する誤り / 検出しない誤り(2026-10 時点)

**検出する(指摘タブに出る)**

| 分野 | 検出する誤り |
|---|---|
| HARA | S/E/C の範囲外・欠落、ASIL の付いた事象に安全目標が無い、安全目標の ASIL と事象の最大 ASIL の不一致、FTTI・安全状態の未設定 |
| 安全機構の FTTI | 紐づく安全目標の FTTI を超える(`MECH_FTTI_EXCEEDS_GOAL`) |
| 意図機能・安全機構の ASIL | 紐づく要求より低い ASIL、要求に紐づかない元 ASIL の表記(偽装)、要求に紐づかない QM(ASIL の付いた安全目標があれば意図機能はエラー、安全機構は警告) |
| ASIL 継承 | 要求の ASIL が上位・安全目標より低い(分解によらない引き下げ。分解先の**子孫**は、元 ASIL の表記ではなく**実際の ASIL** で比較する)、元 ASIL の偽装(分解先でも、その子孫(親と同じ元 ASIL)でもない `A(D)`)、ASIL 付きの安全目標に要求が無い、親子の循環 |
| デコンポジション | 表にない組み合わせ、元 ASIL の不一致、同一要素・祖先/子孫の要素への配置、未配置、独立性の根拠の欠落(エラー)と形だけの根拠(警告)、分解先が分解元の子でない、再利用・二重分解・自己分解・循環 |
| FTA | 循環、未知のノード、入力の無いゲート、件数・時間の打ち切り(いずれも「結果は不完全」。0 件を安全と表示しない)。確率の上限は、未展開の事象・範囲外の確率があれば出さない |
| FMEA・ネット | 上下のリンクの範囲外、故障ノードの孤立、機能の分解漏れ、AP 表の網羅性・重複・単調性、AP 表が非公式/出典未確認(画面・CSV・レポートに明記) |
| 参照 | 存在しない要素・故障ノード・要求への参照、ID の重複 |

**検出しない(人が判断する)**

- **AI の提案が評価値を書き換えたこと自体**は、リスクを下げる変更(重大度・発生度・検出度の低下、QM の追加)なら承認時に**確認を求める**が、その変更が**正しいか**は検出しない。差分は `aiChanges` に残る(サーバーだけが書く。保存・履歴の復元で追加・削除・書き換えはできない)。人の保存の差分は監査ログ(`safety.diff`)に残る(確認は求めない)。
- FMEA の重大度と HARA の S の整合(FMEA 側で重大度を下げても、HARA の S と照合しない)。
- 意図機能・安全機構の ASIL を、要求に紐づけずに設定した場合の妥当性(警告のみ)。

- 独立性の根拠が**内容として妥当か**(文字列の形式のみ検査)。依存故障解析(DFA)・FFI そのものの正しさ。
- 故障モードの網羅性、S/O/D の評価値の妥当性、安全機構が故障を**物理的に**検出・対処できるか(例: 短絡故障をゲート遮断で対処できるか)。`coversFailureIds` は参照の存在のみ検査。`diagnosticCoverage` は、検出度(D)との**目安の整合**(high → D≤3、medium → D≤5。標準に根拠のある閾値ではなく、見直しを促すための経験則)のみ検査する(`MECH_DC_D_MISMATCH`、警告)。SPFM/LFM は下の節のとおり算出するが、PMHF は算出しない。
- FMEA で複数の影響を持つ故障の重大度は、最上位の影響から継承した**最大値 1 つ**で扱う(影響ごとの重大度は持たない)。
- パズルビューの「整合」は、**このツールが検査している範囲**で指摘が無いことを示す。検査していない領域(上記)は整合と区別されない。

## AI の扱い

- AI は提案のみ。承認した変更には、**提案者(依頼した人)・承認者・時刻・AI の提供元**が `safety.json` の `aiChanges` と監査ログに残る。`FUSAMOD_AI_SEPARATE_APPROVER=1` で、依頼した本人による承認を禁止できる(認証を設定しているとき)。
- AI の提案を承認しても、**新しいエラーが増える提案は適用されない**。ただし、承認者が内容の妥当性を確認する責任は変わらない。

## ハードウェアメトリクス(SPFM / LFM)
`hardwareFailureModes`(故障率 FIT・種別・診断カバレッジ。**利用者が入力**)から、ISO 26262-5 の SPFM = 1 − Σ(λSPF+λRF)/Σλ、LFM = 1 − Σλ潜在/(Σλ − Σ(λSPF+λRF)) を算出し、**安全目標ごとに**(各故障モードの `goalIds`。省略はすべての目標)ASIL に応じた目標値(B: 90/60、C: 97/80、D: 99/90 %)と比べる(未達はエラー)。DC を主張する故障モードには、担う安全機構(`mechanismId`)と根拠(`rationale`)を求める(無ければ警告)。DC が機構の区分(low 60% / medium 90% / high 99%)の上限を超えるとエラー。ASIL B 以上の目標があるのに故障モードが無いときは `HW_METRICS_MISSING`(警告)。手計算との一致をテストで確認している。
**限界**: 故障率・分類(単一点/多重)・診断カバレッジの**妥当性は検査しない**(入力の範囲・機構の区分との整合・根拠の有無のみ)。PMHF(または確率的な評価)は算出しない。潜在故障の診断間隔・被曝時間は扱わない。安全な故障の割合は入力値。
